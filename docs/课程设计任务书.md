# 26271-操作系统设计综合实践

## 一、课程基本情况

- 时间：26271小学期，共3周，第1~3周，2026-08-31 ~ 2026-09-20
- 学生：软件工程2023级、网络空间安全2024级

## 二、课程目标

> 已有 C 语言基础，了解操作系统基础概念；21 天是集中课设实践周期，不做完整 OS 从零手写，聚焦内核二次开发、模块扩展、实验复现、小课题研究报告。
> 学生分组完成，每组3~4人，允许学生合理使用AI工具，该行为不视为作弊，凡使用AI工具的组，需在设计实现文档等开发相关文档中声明AI工具、相关大模型等的名称及使用场景，并在git commit记录、开发相关文档、项日设计文档及答辩PPT中单独章节说明AI工具的成果，以及与AI工具的交互记录等。

可选实践方向（xv6 /rCore 两大主流平台）
- [Xv6, a simple Unix-like teaching operating system](https://pdos.csail.mit.edu/6.828/2026/xv6.html)
- [rCore-Tutorial-Book 第三版](https://rcore-os.cn/rCore-Tutorial-Book-v3/index.html)
- [操作系统综合实践课程设计任务书（基于XV6-RISC-V）](https://docs.qq.com/markdown/DUmFydVdaYWx0bkhC?) 
- [操作系统综合实践课程设计任务书（基于rCore内核）](https://docs.qq.com/markdown/DUmJNRHZiRHJoZkhq?)

## 三、成果交付物

可编译运行的内核源码、用户态测试程序、完整课程设计报告、运行截图与测试日志、答辩PPT及演示视频。

## 通用考核标准与交付成果

### 1\. 考核评分标准（100分）

环境搭建与内核正常运行（10分）、核心模块功能完整（45分）、自定义系统调用/扩展功能可用（20分）、测试充分且性能分析合理（15分）、小组分工明确\+报告规范（10分）

### 2\. 统一交付成果

可编译运行的XV6改造源码、用户态测试程序、完整课程设计报告、运行截图与测试日志、答辩PPT（可选）

## 三、评价

>定位：评价分为 4 个维度：代码实现、测试验证、文档报告、理解与分析；设置 4 个等级：不及格、及格、良好、优秀，每一档给出可观测、可核查的客观判定标准。

### 评价总原则

1. 21 天只考核**对现有教学内核的修改与扩展**，不考核从零编写 OS；
2. 允许存在少量非致命 bug，重点看：目标是否达成、测试是否到位、对原理的理解深度；
3. 小组项目需要区分：整体成果 + 个人负责模块，不能只看最终产物。

### 四大评分维度（权重）

1. **代码实现 40%**：功能完成度、代码质量、版本管理
2. **测试与验证 25%**：测试用例、实验数据、现象复现
3. **报告文档 20%**：需求、设计、流程图、问题复盘
4. **原理理解与分析 15%**：能不能解释为什么这么做，对比分析，不是只贴代码

### 分等级客观判定标准

#### 🔴 不及格（＜60 分）

**可观测现象（满足多条即判定）**

1. 环境都没有跑通，原版 xv6/rCore 无法在 QEMU 正常启动；无有效修改代码。
2. 仅有少量注释改动，没有完成任何预设扩展功能；所有目标均未实现。
3. 报告大量复制网上资料，没有自己的实验截图、没有自己的分析；代码与报告描述不一致。
4. 答辩无法说清自己修改了哪些内核文件，不清楚进程 / 调度 / 内存的基础流程。


>典型场景：时间不够，直接下载网上开源成品当作自己成果；跑不起来，只有文档没有可运行代码。

#### 🟡 及格（60‑74 分）

**底线：完成基础目标，能跑，但是深度不足**

1. **代码 (40 分拿到 22‑26)**

- 环境搭建成功，内核可以正常启动运行；完成**1 个基础扩展功能**（例如新增 1 个系统调用；简单修改调度逻辑）。
- 修改点少，代码简单；存在明显 bug，部分场景会 panic；没有做代码规范化，无 git 版本管理。

2. **测试 (25 分拿到 14‑17)**
- 仅有简单手工测试，1‑2 个简单用例；只有现象截图，**没有定量数据**；异常场景完全不测试。

3. **报告 (20 分拿到 12‑14)**
- 报告结构完整，有需求、简单设计；流程图简陋；大量摘抄教材 / 网络，自己思考较少；缺少问题排查记录。

4. **理解 (15 分拿到 9‑11)**
- 能说清自己做了什么，但是对底层原理理解浅薄；无法解释修改会带来什么副作用，不会对比原版内核行为。

>例子：成功加上一个系统调用，能返回简单数值；但是没有压力测试，报告主要抄资料。

#### 🟢 良好（75‑89 分）

**核心：功能完整，测试充分，理解到位，小瑕疵存在**

1. **代码 (40 拿到 30‑35)**
- 稳定实现预定的 1‑2 个核心扩展功能，内核可以稳定运行，偶发边界条件 bug，不影响主体功能。
- 修改模块边界清晰，关键位置有注释；使用 git 管理，提交记录可见；没有大段复制粘贴网络代码。
>例：MFQ 调度完整实现，普通多进程场景调度正常；个别极端进程场景有小问题。

2. **测试 (25 拿到 19‑22)**
- 有多组测试用例：正常场景 + 边界场景；具备对比实验（原版 vs 修改版）；有运行时间、周转时间、缺页次数等**定量数据**，有简单图表。
- 提供测试脚本，现象可以复现。

3. **报告 (20 拿到 15‑17)**
- 需求明确；画出关键模块流程图；清晰说明修改了哪些内核文件、改动逻辑；记录遇到的 2‑3 个真实 bug 以及解决过程；不大量抄袭。

4. **理解 (15 拿到 12‑13)**
- 可以讲清楚原有内核逻辑，以及自己改造点；能分析实现带来的优缺点；知道自己实现方案的局限。
>典型表现：MFQ 调度，多组测试对比 RR，有周转时间统计，报告完整，边界条件偶现异常。

#### 🔵 优秀（90‑100 分）

**核心：功能健壮、严谨测试、有思辨，看到学生真正钻研内核**

1. **代码 (40 拿到 36‑40)**
- 预定功能全部实现，边界场景经过处理，内核整体稳定；
- 代码结构良好，注释到位；git 提交历史清晰，每一步迭代可见；
- 针对自己实现的缺陷做了针对性优化；不是简单复制网上现成实现，有自己的设计取舍。

2. **测试 (25 拿到 23‑25)**
- 测试集完备：正常负载、高并发压力、边界异常；
- 多组可复现对比实验，定量指标完整（响应时间、吞吐量、缺页率等）；图表规范；客观指出自己方案的性能短板。

3. **报告 (20 拿到 18‑20)**
- 有完整需求分析、方案选型对比；流程图、数据图表规范；
- 详细记录调试过程，对 panic、bug 有溯源分析；
- 能客观写出现有实现的不足与未来改进方向。

4. **理解 (15 拿到 14‑15)**
- 清晰掌握内核原有机制；能够横向对比不同算法 / 方案；
- 答辩可以回答扩展问题：例如 “你的调度算法在什么场景下会变差？为什么？”，具备批判性思考。
>示例：MFQ 调度，处理进程优先级变化、进程退出等边界；多组压力测试，对比 RR，客观分析本实现的缺陷；报告完整，git 迭代清晰。

### 小组项目补充评价要点（避免搭便车）

1. 必须核查：git 提交记录、个人分工文档、答辩时每个人独立回答自己模块的问题；
2. 小组整体成果优秀，但某成员无法解释自己负责模块 → 该成员降档；
3. 禁止：一人写完全部代码，其他人只写报告。

### 常见扣分点（客观扣分项）

1. 直接照搬 github 完整项目，无自己改造，直接扣到及格及以下；
2. 只有文档，代码无法运行，直接不及格；
3. 有功能，但是**完全没有对比测试、没有定量数据**，最高只能给到良好；
4. 报告大段复制网络资料，无自己实验内容，降一档。
