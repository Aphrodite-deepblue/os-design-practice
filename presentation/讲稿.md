## 1. 封面｜0:20

大家好，我们是天津大学软件学院第 35 组。本次汇报介绍我们在 xv6-RISC-V 上实现的静态优先级调度，以及用于缓解饥饿问题的 Aging 机制。

## 2. 项目概览｜0:55

原版 xv6 主要采用轮转方式选择可运行进程，所有进程在调度层面的地位比较接近。我们的目标是增加一个简单、可解释的静态优先级：数值越小，优先级越高；同时保留同优先级进程的基本公平性。

五位成员按模块分工：袁晟棋负责进程字段和 fork 继承，刘文睿负责调度器，赖弈铭负责 Aging，党正清负责系统调用和 `nice`，吴雨桐负责测试与集成。这样划分能够减少核心文件中的交叉修改。

## 3. 总体设计｜1:05

从用户角度看，可以使用 `nice` 查询或设置进程优先级。命令进入 `getpriority` 或 `setpriority` 系统调用，内核再修改进程的 `priority` 字段。调度器每轮根据可运行进程的优先级作出选择，Aging 则在等待过久时对这个优先级进行有限的提升。

整个设计只保留两个新状态：`priority` 表示静态优先级，`wait_ticks` 表示等待时间。优先级范围统一为 0 到 31，默认值为 10，0 是最高优先级。

## 4. 模块 A：进程优先级数据结构｜1:00

这一页只讲进程数据。每个进程增加 `priority` 和 `wait_ticks` 两个字段。优先级范围是 0 到 31，默认值为 10，数值越小代表优先级越高。

字段会贯穿进程生命周期：创建时初始化，fork 时子进程继承父进程优先级，调度成功后清零等待计数，进程释放和槽位复用时重置字段。fork 读取父进程优先级前先获取父进程锁，复制的是受保护的快照。

## 5. 模块 B：静态优先级调度｜1:30

调度器使用两轮扫描。第一轮遍历进程表，对等待进程执行 Aging，并找出当前可运行进程中的最小优先级。第二轮从 `next_index` 开始扫描，选择该优先级下的第一个 `RUNNABLE` 进程。

这样做把优先级判断和同级选择分开。`next_index` 让同优先级进程轮流成为候选者。真正切换前，调度器还会重新检查状态并取得进程锁，以应对多 CPU 下的状态变化。Aging 使用 `AGING_INTERVAL=50`，等待达到阈值后优先级向 0 方向提升一级。

## 6. 模块 C：系统调用与用户态命令｜1:15

这一页对应优先级控制接口。`setpriority` 用于设置目标进程优先级，`getpriority` 用于查询；系统调用号分别是 23 和 24，用户态声明、汇编入口和内核实现沿用 xv6 原有注册流程。

内核会检查 PID 是否为正数、目标进程是否存在，以及优先级是否位于 0 到 31。设置成功后会清零 `wait_ticks`，避免旧等待历史立即触发 Aging。用户可以使用 `nice pid` 查询，也可以使用 `nice pid priority` 设置。

## 7. 模块 D：调度统计｜1:15

统计模块需要回答三个问题：不同优先级进程何时完成、Aging 等了多久、测试过程是否稳定。当前内核保留 `wait_ticks`，专项测试则输出 `METRIC` 和 `AGING_RESULT`，由运行器保存成日志与结构化结果。

单 CPU 的 `prioritytest` 输出 6 条指标，3 CPU 输出 12 条；两组测试的 `agingtest` 和 `usertests -q` 都通过。当前没有把调度次数、运行时间新增为 `struct proc` 的持久化字段，这是为了保持实现边界简单。仓库链接放在页面底部，可以直接点击。

## 8. 模块 E：用户态测试｜0:30

测试覆盖默认值、优先级边界和非法参数，比较不同优先级进程的调度机会，检查同优先级公平、fork 继承、Aging 生效和进程退出后的稳定性。实际入口是 `prioritytest`、`agingtest` 和 `usertests -q`，运行器会保存原始日志、`results.json` 和 `metrics.csv`。

单 CPU 与 3 CPU 两组都返回 PASS；Aging 分别在 136 和 45 ticks 内将目标优先级从 3 提升到 0，8 个高优先级竞争进程仍存活且未超时。这里展示的是功能回归结果，不把一次本地运行解释成性能结论。
